# 08 Messaging (Photon)

**Spec:** 6.15, G16, A8. **Depends on:** 01, 02, 07. **Feeds:** the demo's main interface (and the Photon challenge).

Goal: users create intents, answer questions, approve, and receive contacts by text. The channel sits behind an adapter so everything else runs against a terminal adapter in development.

## Components (`messaging/`)
```
adapter.ts       interface ChannelAdapter { start(onInbound), send(phone, text) }
photon.ts        Photon Spectrum adapter (spectrum-ts)
terminal.ts      Spectrum terminal provider or a plain stdin/stdout fake, for dev and tests
inbound.ts       resolve user, route message
outbound.ts      listens to notify events, applies rules, renders templates, sends
templates.ts     one function per notification kind
linking.ts       phone <-> account linking
rules.ts         dedupe, rate limits, queueing
```
Select the adapter with `CHANNEL`. Both implement the same interface, so no other code knows which is active.

## Photon setup (read the Photon docs before coding)
- Use the Spectrum Node SDK (`spectrum-ts`) with `PHOTON_PROJECT_ID` and `PHOTON_PROJECT_SECRET`. Pick Stable or Beta docs and stay on it (see overview).
- Photon delivers webhooks at least once and only to public HTTPS endpoints. If using webhooks, verify the signing secret and dedupe by provider message id (`sms_log.provider_id` is unique).
- A Photon project can only message people it knows. For the demo, register the team's phones in the Photon dashboard ahead of time. For real onboarding, the user texts the line first.
- Confirm that the line falls back to SMS for non-iMessage numbers. Note the result in the repo README.

## Linking a phone to an account
1. After Clerk sign-in, the web app shows the Photon number and a 4-digit code (`POST /me/link-code`).
2. The user texts the code to the line. Inbound handler matches the code, sets `users.phone` and `phone_verified`, replies "Linked."
3. Unknown numbers that text anything else get one reply with linking instructions. No other processing.
4. Seeded demo users have phones preset with `phone_verified = true`.

## Inbound routing (`inbound.ts`)
Order of checks for a message from a linked user:
1. **Reply code:** pattern like `Y A3`, `N A3`, `A3 yes`, or a bare `yes`/`no` when the user has exactly one open request. Look up `reply_codes`. If several are open and no code is given, reply listing the codes.
2. **Open draft question:** if the user has an unanswered draft, treat the message as the answer (`answerDraft`).
3. **Near-miss reply:** "OK to $320", "go to 320". Parse the number, then ask "Raise your limit to $320? Reply YES." On YES, update `minNetCents` and create a new intent version (slice 02).
4. **Commands:** `STATUS`, `WITHDRAW <code>`, `STOP`, `HELP`.
5. **Otherwise:** treat as a new intent (`createDraft`).

Use deterministic regex for 1, 3, 4. Only step 5 and draft answers use the LLM (slice 02 parser). Never let free text trigger an approval: approval needs a recognized code and an affirmative token.

## Outbound (`outbound.ts`)
Subscribe to `notify` events (`{ userId, kind, payload }`). Kinds and templates:

| Kind | Content | Limit |
|---|---|---|
| `draft_question` | the question | while draft open |
| `draft_confirm` | parsed draft in plain words, "Reply YES to post" | once per draft version |
| `nothing_found` | "Nothing I can assemble yet. Closest: lowest ask $315, you're at $300. Reply OK to $320 to raise your limit." | once per intent version, min 24 sim hours |
| `approval_request` | what you give, to whom (handle), what you get, cash, difference, "includes N other participants you won't deal with", reply code | pending cap 3 |
| `approved_ack` | "I'll tell you when the others approve." | immediate |
| `waiting_update` | after 24 sim hours waiting | once per arrangement |
| `dissolved` | arrangement fell through | once, approved users only |
| `committed` | counterparties' names and contacts, checklist | all participants |
| `tolerance_confirm` | "Raise your limit to $320? Reply YES." | on demand |

Rules:
- Dedupe by `(userId, kind, refId)` in `rules.ts`.
- Keep texts under about 320 characters. Split the commit message into two sends if needed.
- Skip quiet hours entirely for v1.
- Log every send and receive to `sms_log` with the provider id.
- On send failure, retry twice, then leave the state visible in the app. The web app is the source of truth.
- Reply codes: short, 2 characters (letter plus digit), unique per user among open requests, stored in `reply_codes`, expire with the request.

## Prompt-safety
Handles and any text from other users are not included in outbound messages except the counterparty handle string, which is generated by the system. Never include another user's free text in an SMS.

## Acceptance
- With `CHANNEL=terminal`, the full S1 flow runs from three terminal sessions.
- A fresh phone linked by code can then text "selling my friday ticket for $300" and get a draft question or confirm.
- Photon webhook replay of the same message id sends one reply only.
- "yes" with two open requests gets a clarifying reply, not an approval.
- "OK to $320" after a `nothing_found` produces the tolerance confirm, and YES creates a new version and triggers a search.
- No outbound message in any test contains a bound value, a third party's handle, or another user's free text.

## Notes
- Spectrum can also run voice, groups, and reactions. Ignore them for v1.
- Keep adapter code under about 150 lines. Business logic stays in `inbound.ts` and `outbound.ts`.
